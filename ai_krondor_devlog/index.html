Krondor Journal

Rebuilding Betrayal at Krondor (1993) as readable C that runs in the browser, one piece at a time. Newest first. Every claim about the original is checked against the real game running in DOSBox.

All posts

    Reading the signs

    Oct 13, 2026

    Clicking a signpost now reads it. Like bodies and chests, a sign is a "container" keyed by its position in the world, and its text is a dialog key in one of the container's optional blocks. Signs weren't in the save, though. The original looks in two places: first the save, then a file called OBJFIXED.DAT, which has the same format and holds the things that never change (signs, graves and such). A directory in the save gives each zone's starting offset in both. The C version now does the same, which also opens the door to graves, piles and the rest.

    To test it, I needed the original standing in front of the same sign. I loaded the chapter 1 start in DOSBox, wrote a camera position and heading straight into memory, and took one step so the game caught up. That gave the same view in both. The comparison showed one more detail: the original moves the text box onto the clicked object and grows it out of that point over a few frames. We were drawing it at the top of the view.

    Things that wear off

    Oct 13, 2026

    A lit torch, a light spell or a spell like Scent of Sarig lasts a while and then runs out. The original tracks all of these in one small table: up to 20 records of {type, which one, seconds left}, saved with the game. Every time the clock moves, each record is counted down and told how long it has left. A light record sets the torch's glow (fainter in its last minutes). A spell record keeps a bit set in a "spells in effect" word, which combat already reads for sneaking. Two more kinds set or clear a story flag when their time is up.

    Torches use it now. Double-click one in the inventory and it's lit for the hours its item data says. The world takes on a warm tint at night, using the palette code from the nightfall post. When the time runs out the torch burns down and one is used up. Using a lit torch puts it out (which also uses it up, as in the original). None of my test saves has a torch, so I added two test options: --give puts an item in the first member's pack, and --use uses it, once the main view starts.

    Making camp

    Oct 13, 2026

    With time passing, camping was next. The campfire button opens a screen that replaces the 3D view with a day-and-night dial of 24 hour markers. It also lists each member's health and stamina and how many rations they carry. Click an hour and the party sleeps until then, while a highlight sweeps around the dial a quarter of an hour at a time. "Until healed" keeps going until everyone is back to 80%.

    Under the hood, each hour is one call to the time routine from the last post, with resting turned on. So the party eats once a day, conditions run their course and health returns, but only up to 80%: the original's hourly healing caps a full night's rest there. After twelve hours of sleep any sickness is gone. You can't camp with monsters standing nearby. In daytime the dial even casts a sundial shadow (a triangle, darkened through a table that maps each colour to the closest one ten steps darker).

    The ground shimmers on purpose

    Oct 13, 2026

    Once the trees matched, the walking comparison still had the whole grassy ground speckled red, though it had matched right after loading the game. The pattern wasn't shifted by any amount I could find. The original's pattern-fill code explained it: every pattern (grass, hillsides, the ground band) starts at a fixed place in the texture page plus a value at DGROUP:0434. That value is set to rand() & 15 after every step and every turn. So each time you move, all the ground textures jump by a random few bytes. It's a cheap way to make the ground feel like it's passing by.

    The C version does the same now. For the comparison I read the original's value after the sixth step (12) and forced the C version to use it through a new test option (--jitter). With that, the frames differ in only 603 pixels: a few polygon edges and the mouse pointer.

    Then I projected polygon corners the original's way (integer coordinates, truncating division) and tried a few rules for which pixels a scanline covers. Rounding each edge's crossing worked best, which brought the difference down to 378 pixels. The exact answer is the original's edge walker, which has a separate stepping routine for each kind of slope. It's on the list, but the 3D view is now nearly pixel for pixel the original's.

    Trees in the right places

    Oct 13, 2026

    The comparisons kept showing differences in the trees. With the new breakpoints I could ask the original directly: stop wherever it draws a sprite and read every number it passes along (where on the screen, how big, which fog table). Then compare them with ours. The far trees were within a pixel, but the near ones were 15–25% too small, and two trees at the right edge were missing. Four things were behind it:

    • Size. The original projects an object's radius at its near side, r·512/(z−r), not at its centre. It uses the same number to pick the level of detail.
    • Culling. An object is skipped only when the sphere's innermost corner is off screen. Ours was stricter, which lost the two edge trees.
    • Integers. The scale factor, width, height and anchor are all 22.10 fixed point, and far objects' coordinates are halved until they fit in 16 bits. Drawing columns step by 16.16 fixed point, but rows keep only the top 8 bits of the fraction.
    • The sine table. Our trees were still a pixel low, by an amount that grew with distance. That's a tilt: the camera's pitch of 280 units behaves like 272, because the original's sine table has 4096 steps per turn. (The horizon line still uses the exact angle.)

    Now every sprite in the test scene matches the original's numbers exactly. Two last details surfaced in the pixel comparison:

    • Row stepping. The tree interiors still had streaks every few rows. The scaler starts its row fraction from the wrong byte: the high byte of the starting row, which is almost always 0, instead of the fraction it just computed. We do the same now.
    • The horizon. The horizon line is truncated, not rounded. That moved the distant mountains up one row.

    Time passes

    Oct 13, 2026

    With lighting done, the clock had to move. Searching the code for the game time found many readers but no obvious writer, and the decompiler couldn't make sense of the code around it. So I rebuilt DOSBox-X with its heavy debugger, which adds memory breakpoints, and set one on the clock. One step forward stopped the game inside a function in an overlay (502B:08E7) that adds a number of seconds to the clock. A step costs 120 seconds at normal speed. That comes from the same small file as the step length (MOVEMENT.DAT), and underground a step costs a quarter of that.

    Besides moving the clock, that function checks whether the hour or the day has changed:

    • Every day each member eats one ration. Spoiled rations fill you but make you a little sick; poisoned rations poison you and don't fill you. With nothing to eat, Starving goes up 5%. Near-death wears off by 1–10% a day, faster when Healing.
    • Every hour each condition changes by its amount in the CONDITION table: sickness and poison get worse, drunkenness and healing fade. Health changes too: down while sick, poisoned or starving, up while healing.
    • After 17 hours without sleep, someone yawns and says the party needs rest. After 18 they start losing health every hour.
    • Every 30 days each member's maximum health and stamina go up by one.

    One trap with the new breakpoints: they're only checked when the machine is resumed from the debugger. My usual way of pausing and resuming (freezing the machine) runs the plain CPU core, which never checks them. That's now noted in the DOSBox notes for next time.

    Nightfall

    Oct 13, 2026

    The restored "steve" game in the last post looked darker in the original, because the original shades the world for the time of day. I dumped the original's palette in that scene and compared it with the zone's palette file. The first 112 colours (the panel, portraits and text) were untouched. All 144 world colours were about half as bright, but not exactly: 51 became 24 while 10 became 6. So it's a curve, not a plain scale.

    Searching for code that uses the zone's palette led to a small module of about 30 functions (segment 2CBC). It keeps the loaded palette and three working copies, and blends the world colours towards a target colour in up to three passes: a teal haze, then a tint from a light source (a torch's warm yellow, green underground, a blue spell light), then black for the night. Each pass moves a colour (distance − 1) × strength / 64 of the way, using two lookup tables. The light level is full from 8:00 to 17:00, 15 out of 64 from 20:00 to 4:00, and changes linearly at dawn and dusk. The "steve" save is at 19:12, which gives level 29. Running the formula on the zone palette at that level gives the original's palette byte for byte (all 768).

    The torch and spell tints are in the C code too, waiting for torches and light spells to switch them on. Time doesn't pass yet in the C version, so for now a scene stays as dark as the moment it was loaded.

    Saving and restoring games

    Oct 13, 2026

    Restore Game and Save Game work now, with the original's screens: a list of save directories, a list of games, scroll bars, and (when saving) text fields for the directory and the game's name. The saved files use the original format: a 100-byte header with the save's name, then the whole working save. Games saved in the original can be restored here, and the other way round. In the browser, saves are kept in the browser's own storage (IndexedDB); the installation's saved games are listed too.

    The screens came together in the usual way: build, compare with the original, fix. The list boxes, scroll bars, labels and text fields are general pieces the original uses on several screens, so they are separate reusable code now. The comparisons caught a few details: the scroll bar shows its marker even with a single entry; icons are centred by halving each size separately; save slot 0 is always listed as "Bookmark"; and text fields keep the parchment behind them instead of filling it.

    Searching the body, and getting text exactly right

    Oct 12, 2026

    You can now click things in the 3D view. The original keeps a list of the last ten clickable things it drew, each with a box on the screen. Whether something counts depends on its type and how close it is (a table in DETECT.DAT). A click goes to the most recent box under the pointer, then to a handler for that type. The first handler is bodies. Left-click the assassin on the road and the party searches him: a short text, then the inventory opens on what he carried, ready to drag onto your characters. Whatever you take stays taken, because the container is written back into the saved game.

    Pixel comparisons kept turning up the same small problem: a line of text breaking one word earlier or later than in the original. Reading the original's layout code explained it. When the character that doesn't fit is itself a space, the word before it stays on the line. Two more details came out too: text is centred vertically without subtracting the last line's spacing, and boxes at x=13 get no frame. Every text compared since then matches the original line for line.

    The same session fixed an older bug in the chapter-opening scenes. The forest was missing behind the characters, because the parchment backdrop was drawn over the picture instead of around it. Speakers' name tabs were also 10 pixels too high.

    The character sheet, pixel for pixel

    Oct 12, 2026

    Right-clicking a portrait now opens the character sheet: the character's portrait and name, health, stamina, speed and strength, any conditions, and the twelve skills as sword-shaped bars. Clicking a skill marks it for training with a red gem, which affects how quickly it improves.

    Getting there took two rounds of comparing. The first C version showed a black screen with a garbled portrait: I had the palette merge backwards. The portrait's palette only fills colours 16-111, the range its pictures use, and the screen keeps its own colours elsewhere. After that fix, the pixel diff showed one remaining difference: every skill percentage was one pixel too high. That was a misread register in the original's code. One more fix, and the diff came back empty except for the cursor.

    Right-click for the details

    Oct 12, 2026

    Right-clicking an item now shows what the original shows. The item glides aside, with its name, its condition or charges and its state ("Using, Repairable"), and its description appears beside it. Weapons, armour, quarrels and magic items get a More Info button that opens a table: base damage and accuracy for thrusts and swings, armour protection, magic on the item, the race it was made for.

    One bug turned up on the way. The conversation code restored the screen after every text, which is right for texts you click away but wiped out descriptions that are meant to stay up while you decide whether to press More Info. One known difference remains: a line containing a character's name sometimes wraps one word differently from the original.

    The inventory, item by item against the original

    Oct 12, 2026

    The inventory screen used to be a picture: you could look at your items but not touch them. Now it works like the original. Click an item to select it, double-click to use it, or drag it: onto another portrait to give it away, onto the equipment slots to equip it, or onto another item to use one on the other (a whetstone on a sword, poison on quarrels). Stacks ask how many to give, with a Share with party option. Keys go onto the party's key ring, and coins go straight into the purse. Behind it are the original's rules for room (20 cells for a character), for sorting, and for merging stacks. Using an item covers equipping, repairs, oils and poisons, herbs, potions with timed boosts, and healing potions with their "Use again?" question.

    This was the first feature built with the DOSBox remote control from the start. Each step was done in the original first, screenshots taken mid-drag, then the same steps were scripted in the C version and the frames compared pixel by pixel. The first comparison caught three of my mistakes. The money wasn't right-aligned. The ring around the current portrait was one pixel off. And while you drag, the box shows a sack (the ground), not the item: I had misread that from an earlier screenshot.

    A small tool came out of this too: the test harness can now lay out every image in one of the game's image files with its index (--bmx INVMISC.BMX,INVENTOR.PAL). That made it easy to see which picture the box shows for what: a sack for the ground, a chest, a grave, a body, a shop sign, the key ring.

    Still to do on this screen: item information (right-click), the character sheet, dropping things on the ground, shops, and a few special items (maps, light sources, and others).

    Taking full control of DOSBox, and what went wrong

    Oct 12, 2026, 22:01–22:36 · 372d5e1 286423e

    To reverse engineer the game accurately it helps to drive the original like a puppet: pause it, inspect memory, press keys, click, and step time forward exactly. DOSBox-X is open source, so it got a patched control channel. A script can now:

    • set breakpoints and get told when one is hit, read registers, and read or write memory;
    • press keys and click, and put the mouse exactly where it should be. The game only reads relative mouse motion, so the script nudges the mouse until the game's own cursor variable says it has arrived;
    • run exactly N milliseconds of game time and then freeze, at up to about 8× real speed;
    • save and load emulator states, and take screenshots.

    It took several tries to get right, and the mistakes were worth writing down:

    Scripts must check their own results. The first recording sent inputs on fixed timers and never looked at the screen. When one skip didn't take, it spent 40 seconds "walking" at a frozen dialog. Every step now checks it worked, and stops with a screenshot if not.
    Pausing through the debugger corrupted the emulator. Now and then the emulated CPU ended up running garbage. Pausing now freezes the emulator directly: 400 pause/run cycles, no errors, and each cycle got 14× faster.
    Save states break the game's file access. After loading one, the game can't create its save file at the chapter map ("An important data file could not be created!"). Anything that touches files starts from a fresh boot.
    The emulator can pop up windows on the desktop. A "Quit DOSBox-X warning" appeared on the user's screen and froze the emulator waiting for a click. All dialogs are now suppressed.

    The full list, with fixes, is in docs/dosbox-agent.md, and a new CLAUDE.md points every future session to it.

    Making the executable readable

    Oct 11, 2026, 13:58 · a8ac7ab

    KRONDOR.EXE is too big for DOS memory, so most of its code lives in overlays, chunks loaded on demand. That confuses disassemblers. tools/deoverlay.py rebuilds a single flat executable, resolving how each overlay refers to the others, so Ghidra can analyse the whole program. Each C function in the reconstruction cites the address of the original routine it comes from.
